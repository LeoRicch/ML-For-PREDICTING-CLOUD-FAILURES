# Implementation and experiment specification

Generator `resource-shortfall-v1` models CPU and memory in abstract units. Default experiments use three servers, 120 ticks, 100 CPU units and 100 memory units per server. A tick represents one simulated minute.

Arrival counts follow a seeded Poisson generator. Base total arrivals per tick are 0.65, 1.45 and 2.7 for low, medium and high activity; rates scale by server_count/3 and multiply by 1.35 in the middle of each three-block cycle or 0.85 otherwise. Each block lasts 12 ticks. Requests are uniformly sampled integer CPU 6–24 and memory 6–26. Required processing durations are uniformly sampled integers 10–30. Server assignment is uniform. Job names are descriptive examples only.

One third of the standard runs at each load include a temporary capacity reduction. Its start is sampled between a quarter and half of the run duration, its duration is 6–18 ticks, its server is selected uniformly, and its capacity factor is uniform in 0.45–0.70. The schedule is retained for reproducibility but never passed to the predictor. A run's random seed and full settings are retained.

At each tick: arrivals are generated; tasks are visited in arrival/ID order; resource allocation is all-or-none with backfilling; allocated tasks progress and clear their shortfall streak; nonallocated tasks increment it; a third consecutive shortfall causes failure. Completed and failed tasks leave the active set. Resource utilisation records allocations during that tick, including allocations used by jobs completing that tick. Active task counts are measured after state transitions. Observations and predictions describe only tasks still active after those transitions.

For an active observation at t, y=1 if failure occurs in t+1…t+5. A normal completion inside that interval establishes y=0 early. Otherwise y=0 is assigned only after follow-up through t+5; incomplete tail windows are excluded from the training/evaluation dataset and kept blank in live exports. A failure later than t+5 does not turn the earlier observation into a positive label.

The seven features are CPU utilisation, memory utilisation, task CPU/current-capacity ratio, task memory/current-capacity ratio, current active-task count, task age and current shortfall streak. Run, task and server IDs, future schedule changes and future outcomes are excluded. Training features require no fitted scaling or imputation; invalid generated values cause preparation to fail.

The default 600-run manifest is partitioned before generation, stratified by load: 360 training, 120 validation, 120 final testing. No task history crosses these partitions. The model search considers 100/200 trees, depth 10/unrestricted and leaf size 1/5; class weighting is balanced_subsample, random_state=42, n_jobs=min(3, logical processor count). Thresholds 0.3/0.4/0.5/0.6/0.7 are selected on validation F1, breaking ties by recall. Final-test scores are computed only after model and threshold selection. The test set is not resampled.

Validation learning curves use 25%, 50% and 100% of the training runs, preserving load representation and using the selected parameters/threshold. They diagnose the value of additional independent runs; they are not final-test tuning. Thirty separately seeded stress runs at CPU and memory capacities 50, high load and temporary reduction are reported separately. Their seeds are 900000–900029, with all other default settings unchanged.

Observation-level results include class counts, confusion matrix, accuracy, precision, recall and F1. Undefined metrics are null and displayed as —. Warning lead time is failure_tick minus the first warning within the preceding five ticks. Failures without eligible warnings count as missed. Task-level detection and false episode counts prevent repeated tick predictions from being presented as independent experiments. Consecutive warning ticks for a task form one alert episode. An evaluable episode is a false alarm if no constituent warning has a positive five-tick outcome. In training reports, episode statistics use evaluable windows only; censored tail windows are excluded.

Reference approaches are the training majority class and warning after two observed shortfall ticks. The latter is a deterministic comparison, not a second learned model. It exposes how much useful prediction is available beyond the simulator's simple failure rule.

No result establishes real-cloud reliability, production failure prediction, SLA savings or automatic prevention. Live experiments retain the model version selected at creation, so a model trained later does not rewrite earlier predictions. Replay serves immutable snapshots saved at each tick rather than adding knowledge of later outcomes.

## Recovery extension and scope of evaluation

User-requested recovery uses a separate spare-capacity scheduler. It is disabled for the saved 600-run training/validation/test experiment. With recovery enabled, CPU and memory allocations for first attempts are computed exactly as before; recovery consumes only leftovers afterward and uses no random draws. Predictor utilisation features remain first-attempt resource utilisation, reflecting priority demand. Total server utilisation in the interface includes background retries. Initial-attempt predictions and failure timestamps are preserved. Recovery attempts receive no ML scores.

Policy spare-capacity-retry-v1 waits at least 3 ticks after an initial failure, admits a queued job on the least-utilised fitting server at utilisation <=0.65, allows one new retry per server per tick, and permits at most 2 retries. A retry restarts progress at zero; 3 consecutive shortfalls end that retry. Subsequent backoff is 3 times the number of retries used. Attempt/server/timing/outcome history is saved with the job.

After the configured workload duration, arrivals cease. Remaining first attempts and retries run for at most 120 additional ticks, stopping earlier when no work remains. Later genuine first-attempt outcomes can resolve previously censored prediction windows; an existing resolved label is not overwritten. First-attempt failures remain failures for the original prediction target even if a retry succeeds. Recovery rates and final operational job counts are separate from the saved ML benchmark. The latter has not been retrained or reinterpreted as a recovery result.
